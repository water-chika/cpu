# c16, a small C like compiler for cpu16

`c16` compiles a small C like language to cpu16 machine code.  It is
deliberately small: the language is only as large as cpu16 can actually run,
and everything it does not support it refuses with a message rather than
miscompiling.

    build/c16 --asm  < program.c16 > program.s      # readable assembly
    build/c16 --hex --sep_with_line < program.c16   # machine words, directly

## Two output paths

The compiler has two ways out, and they are required to agree byte for byte.

**The text path** (`--asm`) writes ordinary cpu16 assembly.  It is meant for
reading, for diffing and for debugging, and it is not a private dialect: the
assembler in this repository, `asm16`, assembles it unmodified.

**The binary path** (`--hex`, `--bin`) goes straight from the compiler's
lowered item stream to encoded machine words.  It never formats a character
and never lexes one back.  It reuses the assembler's own per item encoder,
`asm_encode_statement<asm_cpu16>` out of `asm_kernel.hpp`, so the two paths
cannot drift apart by accident - they share the encoder, and differ only in
whether a string is written in between.

That equivalence is tested, not asserted.  Every `c16_*` simulation test
compiles its program both ways, assembles the text with `asm16`, and diffs
the words before it simulates anything; `backends_c16` does the same on a
generated program of four thousand functions.

Skipping the text is worth about 2.9x on the whole job - see the benchmark
below.

## The language

### Grammar

```
program     = { global | function }
global      = "int" ident [ "=" expr ] ";"
function    = "int" ident "(" [ params ] ")" block
params      = "int" ident { "," "int" ident }
block       = "{" { statement } "}"

statement   = "int" ident [ "=" expr ] ";"
            | ident "=" expr ";"
            | "if" "(" expr ")" block [ "else" block ]
            | "while" "(" expr ")" block
            | "break" ";"
            | "continue" ";"
            | "return" [ expr ] ";"
            | expr ";"
            | block
            | ";"

expr        = oror
oror        = andand { "||" andand }
andand      = bitor  { "&&" bitor  }
bitor       = bitxor { "|"  bitxor }
bitxor      = bitand { "^"  bitand }
bitand      = equality { "&" equality }
equality    = relational { ( "==" | "!=" ) relational }
relational  = shift { ( "<" | ">" | "<=" | ">=" ) shift }
shift       = additive { ( "<<" | ">>" ) additive }
additive    = multiplicative { ( "+" | "-" ) multiplicative }
multiplicative = unary { ( "*" | "/" ) unary }
unary       = [ "-" | "!" | "~" ] unary | primary
primary     = number
            | ident
            | ident "(" [ expr { "," expr } ] ")"
            | "(" expr ")"

number      = decimal | "0x" hex | "'" char "'"
comment     = "//" ... end of line
```

Operator precedence is the C one, lowest first, exactly as the ladder above
reads.  `-` is both binary subtraction and unary negation.

### Built ins

| call | meaning |
| --- | --- |
| `peek(addr)` | read data memory at `addr` |
| `poke(addr, value)` | write data memory at `addr` |
| `out(n, value)` | report `value` as register `rn` at the end of the program |

`out()`'s first argument has to be a literal `0`..`6`.  The values are kept in
memory while the program runs and copied into `r0`..`r6` by the epilogue, so
the testbench, which checks registers, can see them.  `r7` is never reported;
it is the compiler's address register.

`peek` and `poke` take any expression as an address, so `addr` is a runtime
value.  Addresses `0`..`63` are the program's to use.

### Entry and exit

Execution starts at `main`.  `main`'s return value is **discarded** - a
program reports through `out()`.  (Storing it into `out(0)` would silently
overwrite an `out(0)` the program set itself, which is worse than doing
nothing.)  When `main` returns, the epilogue loads the `out()` slots into
registers and spins on a branch to itself.

## What it will not do

These are limits, not bugs.  Every one of them is a diagnostic, not a
miscompile.

* **8 bit unsigned values only.**  There is one type, `int`, and it is a byte.
  Arithmetic wraps.  `<`, `>`, `<=`, `>=` are unsigned comparisons, because
  the carry flag they are built on is an unsigned borrow.  Unary `-` is the
  `neg` instruction, so `-1` is 255.
* **256 instruction words.**  That is cpu16's whole instruction memory, and
  it is the binding limit in practice: a page of source is about a third of
  it.  The compiler refuses to emit more.
* **96 bytes of variables and frames.**  Globals and one fixed frame per
  function share that.
* **No recursion.**  Every function has one fixed frame, so a cycle in the
  call graph would corrupt it.  The compiler walks the call graph and rejects
  cycles by name, including indirect ones.
* **No pointers, arrays, structs, strings or floats.**  `peek`/`poke` is the
  whole memory model.
* **No `%`.**  cpu16 has no remainder instruction.  Write `a - (a / b) * b`.
* **No `for`.**  `while` only.
* **`&&` and `||` do not short circuit.**  Both sides are always evaluated,
  then normalised to 0/1 and combined with `and`/`or`.  A side effect in the
  right hand side happens whether or not the left hand side decided the
  answer.
* **Shift amounts must be literals 0..7.**  cpu16 takes the shift count from
  a 3 bit operand field, not a register.
* **Expressions nest at most 32 deep**, and functions take at most 8
  parameters.
* **`int x = x;` is an error.**  A declaration becomes visible only after its
  own initialiser.
* **Division by zero is undefined** - the hardware produces `x`.
* No preprocessor, no `#include`, no separate compilation: one source file,
  read from standard input.

## How it generates code

### The memory map

cpu16 has 256 bytes of data memory, and the compiler divides all of it:

| range | what |
| --- | --- |
| `0..63` | the program's own space, for `peek`/`poke` and the testbench's `+data` file |
| `64..159` | globals, then one fixed frame per function |
| `160..191` | the expression stack, once it runs out of registers |
| `192..198` | `out(0)`..`out(6)` |

### Registers

There is no graph colouring here, and no liveness analysis.  Expressions are
evaluated on a **value stack**, and the register allocator is the rule that
maps a stack slot to a place:

* slots 0..4 live in `r0`..`r4`,
* slots 5 and deeper live in the spill area at `160 + slot`, and are brought
  into `r5` and `r6` for the one operation that needs them,
* `r7` is never a value.  It carries addresses and branch targets.

So the allocator is: the first five levels of expression nesting are free,
and everything below that costs a load and a store per operand.  That is the
whole of it, and it is the honest description - it is a stack machine with
the top five entries pinned to registers.

The one peephole is that `r7` carries a single entry cache of the constant it
already holds, dropped by any write to `r7` and by any label.  Addresses are
rebuilt constantly - `x = x + 1` materialises `x`'s address twice - and this
is worth about a third of the program size.

### Constants

`imm v s d` writes `(v << s)` and `imm_s` ors it in, three bits of each, so
any byte is at most three groups at shifts 6, 3 and 0.  Zero groups are
skipped, and the first group emitted has to be the assigning `imm`.  One to
three words per constant.

### Comparisons

cpu16 has no set-on-condition, but `sub a b` leaves carry set exactly when
`a < b` unsigned, and `adc` can read it back:

```
lt(a, b)    sub a b r7          carry = a < b
            imm 0 0 dst
            adc dst dst dst     dst = 0 + 0 + carry
```

`gt(a, b)` is `lt(b, a)`; `ge` and `le` are those inverted with `xor 1`.
`eq` and `ne` compare the difference against zero the same way, five words
each.  Conditions are proper 0/1 values, not just branch inputs, so
`out(1, (9 > 2) + (7 == 7))` is 2.

### Calls

Every function has one frame at a fixed address: the return address, then the
parameters, then the locals.  A call at stack slot `d`:

1. evaluate the arguments into slots `d`..`d+n-1`,
2. **then** spill the caller's live slots `0`..`d-1`.  The order matters: an
   inner call inside an argument has to find the outer operands still in
   registers so that it can save them itself,
3. store the arguments into the callee's parameter slots,
4. `la r6 Lret`, store `r6` into the callee's return address slot, `la r7
   entry`, branch,
5. park the result, restore the caller's slots, bring the result back.

The return value is always in `r0`.

## How it runs in parallel

The compiler is staged the same way the assembler is, and each stage is
either genuinely independent or honestly serial.

| stage | unit of work | parallel? |
| --- | --- | --- |
| lex | one source line | yes - count, prefix sum, fill |
| split | the whole token stream | **no** - a linear brace depth scan |
| size | one function | yes |
| lower | one function | yes, work stealing |
| layout | one function | prefix sum, then a parallel fill |
| resolve | one item | yes |
| emit | one item | yes - lengths, prefix sum, write |

Two things are worth saying plainly.

**`split` is serial and cannot be otherwise.**  Finding where each function
starts and ends means tracking brace depth, and brace depth at a point
depends on every token before it.  It is a single linear scan, and at 15 MiB
of source it costs about 3 ms out of 80 - about 4% of a threaded run, and it
is the floor on what threads can ever do here.

**Sizing before lowering is what makes lowering parallel.**  A function's
frame size is the number of locals, and the number of locals is the number of
`int` tokens between its braces - which can be counted without parsing.  So
frames are assigned before any function is lowered, and the functions can
then be lowered in any order, by any thread, with no communication.

`lower` uses a work stealing loop over an atomic counter rather than
contiguous chunks, because real source files have a few enormous functions
and many tiny ones, and contiguous chunks leave cores idle waiting for the
big one.

## Backends

`C16_BACKEND=serial|threads|hip|auto`, `C16_THREADS=n`.  `auto` uses threads
above 2 MiB of source.

The HIP backend runs the per line lexer and the per item emitters on the GPU,
out of the same `ASM_HD` kernel header the CPU backends use - that is why it
cannot produce different bytes.  The prefix sums stay on the host for every
backend.

## Benchmark

`cmake --build build --target benchc`, or `build/c16_bench --sweep`.

20001 functions, 620008 source lines, 15.41 MiB of source, 8.5 M instruction
words, on 24 cores and a Radeon RX 9070 XT (gfx1201, 32 CUs), best of 5:

| path | backend | time | lines/s | MB/s | speedup |
| --- | --- | --- | --- | --- | --- |
| text | serial | 301 ms | 2.06 M | 51.2 | 1.00x |
| text | threads | 83.2 ms | 7.45 M | 185.2 | 3.62x |
| text | hip | 95.3 ms | 6.51 M | 161.7 | 3.16x |
| binary | serial | 240 ms | 2.59 M | 64.4 | 1.00x |
| binary | threads | 64.3 ms | 9.65 M | 239.9 | 3.73x |
| binary | hip | 66.1 ms | 9.38 M | 233.3 | 3.62x |

Run to run variation between the two parallel backends is a few percent, and
which of `threads` and `hip` comes out ahead on the binary path changes
between runs.  The serial numbers are stable.

### What the binary path is worth

The text path is only half the job: something still has to read that assembly
back.  Adding `asm16` in:

| backend | c16 | asm16 | total | binary path | binary is |
| --- | --- | --- | --- | --- | --- |
| serial | 292 ms | 408 ms | 700 ms | 242 ms | **2.89x faster** |
| threads | 80.0 ms | 77.8 ms | 158 ms | 66.6 ms | **2.37x faster** |

That is the measurement the two paths exist to make.  Formatting the text is
the smaller half of the cost; **re-lexing it is the larger half**, and the
binary path skips both.  Comparing only the compilers understates it at
1.20x.

### Where parallelism does not pay

| functions | source | text speedup | binary speedup |
| --- | --- | --- | --- |
| 64 | 0.05 MiB | 0.26x | 0.17x |
| 256 | 0.20 MiB | 0.62x | 0.56x |
| **512** | **0.39 MiB** | **1.09x** | **1.10x** |
| 2048 | 1.57 MiB | 2.68x | 2.84x |
| 16384 | 12.6 MiB | 3.43x | 3.74x |

**Break even is about 0.39 MiB, or 16 thousand lines.**  Below that the
thread pool costs more than the work: at 0.05 MiB threads are four to six
times *slower*.  A real cpu16 program is at most a few hundred lines, so for
every program this compiler can actually run on the hardware, **the serial
backend is the right one and the parallel ones are pure loss.**  That is why
the default is `serial` and `auto` only crosses over at 2 MiB.

3.6x on 24 cores is not 24x, and the reason is the same one the assembler
found: the work per byte is tiny and the memory traffic is not.  `lower`
scales well (100 ms to 11 ms, 9x), `lex` and `emit` scale about 4x, `layout`
is dominated by a serial prefix sum, and `split` does not scale at all.

### The GPU

The GPU is a real backend, it runs, and its bytes match - and it is worth
roughly nothing.

On the binary path it lands within a few percent of 24 CPU cores, sometimes
just ahead and sometimes just behind - a tie.  On the text path it is
consistently **slower**
than the CPU (31 ms of emit against 19 ms), because the text emitter needs
two passes - measure the lengths, prefix sum them on the host, then write -
and so the item array crosses PCIe twice.  The binary emitter needs one pass,
and that single difference is the whole gap.

This agrees with what the assembler session found, for the same reason: per
item compilation is memory bound, a few bytes in and a few bytes out, with
almost no arithmetic in between.  That is the shape of work a GPU is worst
at.  The interesting part is not that the GPU lost but *why* it lost by
different amounts on the two paths - the gap is entirely the extra transfer,
not the kernel.

It is kept because it is cheap, because it proves the shared kernel really is
shared, and because a negative result you can re-run is worth more than an
assumption.
