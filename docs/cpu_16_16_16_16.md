# cpu_16_16_16_16 - a 16 bit word, 16 bit data, 16 registers, 16 bit PC

**Status: the specification.** This document is written before the RTL, and
the RTL and the assembler are both implementations of it. Where they
disagree with this document, they are wrong.

The name is the repository's convention read out in order - *instruction
width / data width / register count / PC width* - so `cpu_16_16_16_16` is a
**16 bit instruction word** over a **16 bit data path**, with **16
registers** and a **16 bit program counter**, i.e. a 64 KiB code space. For
comparison, `cpu16.v`'s module is `cpu_inst16_data8`, which under the same
convention is `cpu_16_8_8_8`; `gpu16.v`'s scalar unit is `cpu_32_32_16_16`.

## 1. The one hard problem

Sixteen registers need a 4 bit field to name one. A three address
instruction - `add rd, rs0, rs1`, which is what `cpu16.v` and `gpu16.v` both
have - needs three of them, which is 12 of the 16 bits, leaving **4 bits of
opcode: sixteen instructions in the whole machine, and no immediate forms at
all.** That is not an instruction set, so the three address form is the first
thing to go.

Two address it is: `op rd, rs` computes `rd = rd op rs`, one register is both
a source and the destination, and the instruction word spends 8 bits on
registers and has 8 left. This is the classical answer (PDP-11, 68000, x86)
and it has a known cost: an operand is destroyed by every operation that uses
it, so a value that is still needed afterwards must be copied first with
`mov`. In exchange, the *other* eight bits are free, and that is what buys
everything in section 3.

The second problem is immediates, and it is sharper than it looks. Any
instruction that wants an 8 bit immediate *and* a destination register spends
8 + 4 = 12 bits on its operands, so **its opcode is 4 bits wide: a whole
sixteenth of the encoding space per immediate instruction.** There is no way
around that arithmetic; the only decision is how many of the sixteen top
level classes are sold for immediate forms, and to which ones. This ISA sells
six of them, and section 3 argues each one.

The third problem is reach. An 8 bit immediate cannot express a 16 bit
constant, and a 16 bit PC cannot be reached by any displacement that fits in
one word. The answers are:

* constants: `movi` (sign extended 8 bit) then `movih` (replace the high
  byte), so **any** 16 bit constant costs at most two instructions, and a
  small one costs one. This is `gpu16`'s `s_imm`/`s_immh` pair one width
  down, and it is why `movi` sign extends rather than zero extends - small
  negative numbers are the common case, and `movih` repairs the high byte
  whenever the sign extension was not what was wanted.
* code addresses: `jmp`/`call` carry a signed 12 bit word displacement
  (+-4 KiB) and the conditional branches a signed 8 bit one (+-256 bytes);
  anything further away is a two instruction `la` (which is `movi`+`movih`)
  followed by `jmpr` or `callr`, which reach the whole 64 KiB.

`cpu16.v` has neither of these: its immediate is `imm3 << imm_shift`, one of a
handful of values, and its only way to a code address is to build one in a
register three bits at a time (the ten word `la` expansion in
`asm_kernel.hpp`). Two instructions for any constant is the single largest
usability difference between this core and `cpu16.v`.

## 2. Instruction formats

Every instruction is exactly one 16 bit word. There are six formats, and
`Inst[15:12]` - the **class** - selects between them.

```
   |f e d c|b a 9 8|7 6 5 4|3 2 1 0|
R  |0 0 op6        |  rs   |  rd   |   class 0x0-0x3: opcode = Inst[15:8]
I  |class  |    imm8       |  rd   |   classes 0x4-0x7, 0xa, 0xb
M  |class  |  rd   |  rs   | off4  |   classes 0x8, 0x9
B  |1 1 0 0| cond  |    disp8      |   class 0xc
J  |1 1 0 1|      disp12           |   class 0xd  (jmp)
J  |1 1 1 0|      disp12           |   class 0xe  (call)
   |1 1 1 1|         reserved      |   class 0xf
```

**R format.** `Inst[15:14] == 2'b00`, so the opcode is the whole top byte and
runs 0x00 to 0x3f: **64 register-to-register opcodes**, of which section 3
uses 35 and leaves 29 free. `rs = Inst[7:4]`, `rd = Inst[3:0]`. Five of them
(`shli`, `shri`, `sari`, `roli`, `rori`) reinterpret the `rs` field as a 4 bit
shift amount, and one (`rd_sys`) reinterprets it as a system register number;
this is exactly `cpu16.v`'s trick of reading `Arg0`/`Arg1` as an immediate.

**I format.** `imm8 = Inst[11:4]`, `rd = Inst[3:0]`. Six classes.

**M format.** `rd = Inst[11:8]`, `rs = Inst[7:4]`, `off4 = Inst[3:0]`.

**B format.** `cond = Inst[11:8]`, `disp8 = Inst[7:0]`, signed, counted in
**instruction words** relative to the following instruction.

**J format.** `disp12 = Inst[11:0]`, signed, in instruction words, relative to
the following instruction.

Class 0xf is reserved and **decodes as an unknown opcode**, as do the 29
unused R opcodes, `cond == 0xf`, and any system register number above 2. That
is deliberate and it is load bearing: the test harness treats "unknown
opcode" as a failure, so a program that runs off its own end - into
uninitialised memory, which reads as `x` and matches no class - fails loudly
instead of quietly computing something.

## 3. The opcode map

### 3.1 R format, `Inst[15:8]`

| op | mnemonic | operands | effect | flags |
|---|---|---|---|---|
| 0x00 | `and`    | rd, rs | `rd &= rs` | Z N |
| 0x01 | `or`     | rd, rs | `rd \|= rs` | Z N |
| 0x02 | `not`    | rd, rs | `rd = ~rs` | Z N |
| 0x03 | `xor`    | rd, rs | `rd ^= rs` | Z N |
| 0x04 | `add`    | rd, rs | `rd += rs` | Z N C V |
| 0x05 | `adc`    | rd, rs | `rd += rs + C` | Z N C V |
| 0x06 | `sub`    | rd, rs | `rd -= rs` | Z N C V |
| 0x07 | `sbb`    | rd, rs | `rd -= rs + C` | Z N C V |
| 0x08 | `neg`    | rd, rs | `rd = -rs` | Z N C V |
| 0x09 | `mul`    | rd, rs | `rd = (rd * rs) & 0xffff` | Z N |
| 0x0a | `div`    | rd, rs | `rd = rd / rs`, unsigned; `rs == 0` gives 0xffff | Z N |
| 0x0b | `mov`    | rd, rs | `rd = rs` | - |
| 0x0c | `cmp`    | rd, rs | flags of `rd - rs`, no write back | Z N C V |
| 0x0d | `tst`    | rd, rs | flags of `rd & rs`, no write back | Z N |
| 0x0e | `shl`    | rd, rs | `rd <<= (rs & 15)` | Z N |
| 0x0f | `shr`    | rd, rs | `rd >>= (rs & 15)`, logical | Z N |
| 0x10 | `sar`    | rd, rs | `rd >>= (rs & 15)`, arithmetic | Z N |
| 0x11 | `rol`    | rd, rs | rotate left by `rs & 15` | Z N |
| 0x12 | `ror`    | rd, rs | rotate right by `rs & 15` | Z N |
| 0x13 | `shli`   | rd, sh | `rd <<= sh`, `sh = Inst[7:4]` | Z N |
| 0x14 | `shri`   | rd, sh | `rd >>= sh`, logical | Z N |
| 0x15 | `sari`   | rd, sh | `rd >>= sh`, arithmetic | Z N |
| 0x16 | `roli`   | rd, sh | rotate left by `sh` | Z N |
| 0x17 | `rori`   | rd, sh | rotate right by `sh` | Z N |
| 0x18 | `ldb`    | rd, rs | `rd = zero_extend(mem8[rs])` | - |
| 0x19 | `stb`    | rd, rs | `mem8[rs] = rd[7:0]` | - |
| 0x1a | `sxb`    | rd, rs | `rd = sign_extend(rs[7:0])` | Z N |
| 0x1b | `min`    | rd, rs | `rd = signed_min(rd, rs)` | Z N |
| 0x1c | `max`    | rd, rs | `rd = signed_max(rd, rs)` | Z N |
| 0x1d | `jmpr`   | rs | `PC = rs & 0xfffe` | - |
| 0x1e | `callr`  | rs | `r15 = PC_next; PC = rs & 0xfffe` | - |
| 0x1f | `rd_sys` | rd, sys | `rd = sysreg[sys]`, `sys = Inst[7:4]` | - |
| 0x20 | `halt`   | - | stop | - |
| 0x21 | `nop`    | - | nothing | - |
| 0x22 | `ret`    | - | `PC = r15 & 0xfffe` | - |
| 0x23-0x3f | | | **reserved**, unknown opcode | |

`jmpr`, `callr`, `halt`, `nop` and `ret` ignore the fields they do not use;
the assembler writes zero into them, and the hardware does not check. `ret`
is a separate opcode rather than an alias for `jmpr r15` so that a
disassembler and a reader can tell a return from an indirect jump.

`shl`/`shr`/`sar`/`rol`/`ror` mask the shift amount to 4 bits, so a shift by
16 or more is impossible to express and there is no "shift by the whole
width" edge case to get wrong. `roli`/`rori` by 0 are the identity.

### 3.2 I format - the six immediate classes

| class | mnemonic | operands | effect | flags |
|---|---|---|---|---|
| 0x4 | `movi`  | rd, imm8 | `rd = sign_extend(imm8)` | - |
| 0x5 | `movih` | rd, imm8 | `rd[15:8] = imm8`, `rd[7:0]` unchanged | - |
| 0x6 | `addi`  | rd, imm8 | `rd += sign_extend(imm8)` | Z N C V |
| 0x7 | `cmpi`  | rd, imm8 | flags of `rd - sign_extend(imm8)` | Z N C V |
| 0xa | `andi`  | rd, imm8 | `rd &= zero_extend(imm8)` | Z N |
| 0xb | `ori`   | rd, imm8 | `rd \|= zero_extend(imm8)` | Z N |

Why these six and not others:

* `movi` + `movih` are not optional: without them there is no way to
  materialise a 16 bit constant at all, and `movih` is also half of `la`.
* `addi` is the loop counter, the stack adjustment and the pointer bump. It
  is the single most executed immediate form in any program.
* `cmpi` is what makes the branch conditions usable - a two address `sub`
  would destroy the value being tested, so without `cmpi` every comparison
  against a constant costs a `mov` and a scratch register.
* `andi` is byte extraction and bit masking (`andi rd, 0xff`), which a 16 bit
  machine that loads bytes does constantly.
* `ori` is the other half of bit setting, and it is what an assembler or a
  compiler uses to merge a field into a word.

`xori`, `subi` and `muli` are **not** here and that is the cost of the
arithmetic in section 1: each would be another sixteenth of the encoding
space. `subi` is `addi` with the immediate negated, which is free.
`xori rd, k` is `movi rt, k` + `xor rd, rt`, two words and a scratch register.
A `muli` is `movi` + `mul`.

Class 0xf is the sixteenth that is deliberately **not** sold. `docs/cpu32_linux.md`
section 3 lists eleven hardware prerequisites this repository has none of -
traps, a timer, CSR access, fences - and every one of them is new
instructions. Keeping one whole class plus 29 R opcodes free is what makes
those additions possible without a second encoding.

### 3.3 M format - load and store with a displacement

| class | mnemonic | operands | effect |
|---|---|---|---|
| 0x8 | `ld` | rd, rs, off4 | `rd = mem16[(rs + 2*off4) & 0xfffe]` |
| 0x9 | `st` | rd, rs, off4 | `mem16[(rs + 2*off4) & 0xfffe] = rd` |

`off4` is unsigned and counted in **halfwords**, so it reaches 0 to 30 bytes
from the base - a struct, a stack frame or a small array, which is what a
displacement is for. Byte access has no displacement form (`ldb`/`stb` in
section 3.1 address `[rs]` exactly) because a byte loop walks a pointer and
`addi` is one word; the two classes that would have been spent on it are
worth more as `andi` and `ori`.

Neither load nor store touches the flags. A loaded value is tested with
`cmpi rd, 0` or with `tst rd, rd`.

### 3.4 B format - the sixteen conditions, class 0xc

| cond | mnemonic | taken when | meaning |
|---|---|---|---|
| 0x0 | `beq` | `Z` | equal / zero |
| 0x1 | `bne` | `!Z` | not equal / non zero |
| 0x2 | `blo` | `C` | unsigned less than |
| 0x3 | `bhs` | `!C` | unsigned greater or equal |
| 0x4 | `bmi` | `N` | negative |
| 0x5 | `bpl` | `!N` | non negative |
| 0x6 | `bvs` | `V` | signed overflow |
| 0x7 | `bvc` | `!V` | no signed overflow |
| 0x8 | `bhi` | `!C && !Z` | unsigned greater than |
| 0x9 | `bls` | `C \|\| Z` | unsigned less or equal |
| 0xa | `bge` | `N == V` | signed greater or equal |
| 0xb | `blt` | `N != V` | signed less than |
| 0xc | `bgt` | `!Z && N == V` | signed greater than |
| 0xd | `ble` | `Z \|\| N != V` | signed less or equal |
| 0xe | `br`  | always | short unconditional branch |
| 0xf | | - | **reserved**, unknown opcode |

`blo`/`bhs` are spelled that way, and not `bcs`/`bcc`, because **`C` here is a
borrow, not ARM's inverted carry**: after `cmp rd, rs`, `C == 1` means
`rd < rs` unsigned. That is the convention `cpu16.v` already uses for `sub`
and `sbb` (`alu_sub[8]` is the borrow out), and keeping it means `adc`/`sbb`
chains read the same way on both machines.

## 4. Flags

Four bits of architectural state outside the register file: **Z, N, C, V**.

* **Z** - the 16 bit result was zero.
* **N** - bit 15 of the result was set.
* **C** - for `add`/`adc`/`addi`, the carry out of bit 15; for
  `sub`/`sbb`/`cmp`/`cmpi`/`neg`, the **borrow** out of bit 15. Computed as
  bit 16 of the 17 bit sum or difference.
* **V** - signed overflow. For an addition of `a + b` giving `r`:
  `a[15] == b[15] && r[15] != a[15]`. For a subtraction `a - b` giving `r`:
  `a[15] != b[15] && r[15] != a[15]`. `neg rd, rs` is `0 - rs`, so it
  overflows exactly when `rs == 0x8000`.

The rule for which instruction writes which flag, stated once:

* **Z and N** are written by every instruction that produces an ALU result:
  the logic, shift, rotate, arithmetic, `mul`, `div`, `sxb`, `min`, `max`,
  `cmp`, `tst`, `andi`, `ori`, `addi` and `cmpi` instructions.
* **C and V** are written *additionally* by `add`, `adc`, `sub`, `sbb`,
  `neg`, `addi`, `cmp` and `cmpi` - and by nothing else, so a multi word
  add or subtract may put logic and shifts between its `add` and its `adc`.
* **Nothing at all** is written by `mov`, `movi`, `movih`, the four memory
  instructions, the branches, `jmpr`, `callr`, `ret`, `rd_sys`, `nop` and
  `halt`.

`cmp` and `tst` write flags and no register; every other flag writer also
writes `rd`.

`adc` and `sbb` read C. Nothing else reads a flag except the branches and
`rd_sys 2`.

## 5. Memory map and addressing

The machine is **Harvard**, like `cpu8.v` and `cpu16.v`: instruction memory
and data memory are separate address spaces with separate ports, and neither
is visible to the other. This is not a claim that a unified space is wrong -
`docs/cpu32_linux.md` section 3 is clear that Linux needs one - it is the
observation that a self modifying instruction memory is a feature `cpu16.v`
already has (`ld_p`/`st_p`) and that nothing in this core needs.

| space | addressing | size | width |
|---|---|---|---|
| instruction | `PC[15:1]` selects a word; `PC` is a **byte** address and is always even | 32768 words = **64 KiB** | 16 |
| data | byte addressed, 16 bit address | **64 KiB** | 8 or 16 |

Both are parameters on the module (`PROGRAM_ADDR_WIDTH`, default 15 word
address bits; `DATA_ADDR_WIDTH`, default 16 byte address bits) so that a board
can build a smaller one, exactly as `gpu16.v` parameterises its program
memory. The *architecture* is 16 bits of each; a smaller build aliases.

**Endianness is little.** The halfword at byte address `a` has its low byte
at `a` and its high byte at `a+1`. Internally the data memory is 32768 words
of 16 bits with two byte enables, so `mem8[a]` is byte `a & 1` of word
`a >> 1`: `a` even selects `[7:0]`, `a` odd selects `[15:8]`.

**Alignment.** A halfword access ignores bit 0 of the effective address -
`ld`/`st` compute `(rs + 2*off4) & 0xfffe`. There is no unaligned access and
no alignment trap; an odd base address is rounded down, silently and
defined. A byte access has no alignment to violate.

The loader ports are `cpu16.v`'s, widened: the host holds `reset` high and
writes one 16 bit instruction word or one 16 bit data word per cycle. Data is
loaded a *word* at a time, not a byte at a time, because the array is words.

## 6. Control flow

`PC` is a 16 bit byte address, always even. `PC_next` is `PC + 2`.

* **Branch** (class 0xc): if the condition holds, `PC = PC_next + 2*disp8`,
  with `disp8` signed - so the reach is -128 to +127 instructions, i.e. -256
  to +254 bytes from `PC_next`.
* **`jmp`** (class 0xd): `PC = PC_next + 2*disp12`, reach -2048 to +2047
  instructions.
* **`call`** (class 0xe): `r15 = PC_next` and then `PC = PC_next + 2*disp12`.
* **`jmpr rs`**: `PC = rs & 0xfffe`, anywhere in 64 KiB.
* **`callr rs`**: `r15 = PC_next`, `PC = rs & 0xfffe`.
* **`ret`**: `PC = r15 & 0xfffe`.

**r15 is the link register.** It is an ordinary register in every other
respect - it can be read, written, added to and stored - and nothing prevents
a program from using it as a scratch register in a leaf function. What it is
not is hardwired: there is no hardware stack, and a function that calls
another function must save `r15` itself, with `st`/`ld` against a stack
pointer of its own choosing. This ISA has no `sp` and no `push`; the calling
convention is a software matter and is not part of this document.

`call` does not save the flags, and a called function is free to change them.

## 7. System registers, halt and reset

`rd_sys rd, sys` reads one of a small numbered set of state, exactly as
`gpu16`'s `s_rd_sys` does, and for the same reason: it is the right shape for
the CSR mechanism a trap architecture will need later.

| sys | reads |
|---|---|
| 0 | `cycles[15:0]` |
| 1 | `cycles[31:16]` |
| 2 | the flags, as `{12'b0, V, C, N, Z}` - so bit 0 is Z, bit 1 is N, bit 2 is C, bit 3 is V |
| 3-15 | **reserved**, unknown opcode |

`cycles` is a 32 bit counter that increments on **every clock edge on which
the core executes an instruction** - that is, every edge while `reset` is low
and the core is not halted. Since every instruction of this ISA takes exactly
one cycle (section 8), `cycles` is simultaneously a cycle count and a retired
instruction count. `rd_sys rd, 0` returns the value **before** this
instruction's own increment, so `rd_sys r1, 0` as the first instruction after
reset writes 0, and as the n'th instruction writes `n - 1`.

`halt` sets a `halted` bit. While halted the core executes nothing, `PC` does
not change, `cycles` does not advance, and no memory access is issued. Only
`reset` clears it. Unlike `cpu16.v`, which has no way to stop, a program on
this core is expected to end in `halt`, and the testbench treats a program
that never halts as a failure - which is `gpu16`'s `s_endpgm` rule, and it
turns "the program ran into the weeds but the registers happened to look
right" from a pass into a failure.

**Reset** is asynchronous and active high. It clears all sixteen registers,
the four flags, `cycles`, `halted`, and sets `PC` to 0x0000. Execution
therefore begins at instruction word 0.

## 8. Timing

**Every instruction retires in exactly one cycle, including taken branches
and including loads.** The core is the same single cycle machine `cpu16.v`
is, and for the same reason: the instruction memory reads asynchronously, so
the word at `PC` is available in the cycle `PC` holds it, and a branch that
writes `PC` on an edge is followed by the target instruction on the next.
There is no branch bubble. (`cpu16.v` carries a `stall`/`stall_counter` pair
for a multi cycle stall it never takes - `stall_active` is always 0 - and
this core simply does not have it.)

A load is issued on the edge that retires it - the data address, the
destination register and the read enable are registered - and the value is
written back on the *following* edge, at the same instant that the
instruction after the load is decoded. That instruction therefore reads the
register file one cycle before the load has written it, and a forwarding
multiplexer on the read side supplies the loaded value instead. The
observable rule is the simple one: **a load's result is available to the very
next instruction**, and load-use costs nothing.

A store is registered on the edge that retires it and the memory array is
written on the following edge, so a load of an address that was stored to by
the immediately preceding instruction reads the stored value.

## 9. Assembly syntax

The assembler is `asm_16_16_16_16`, built from one more ISA description in
`asm_kernel.hpp` exactly as `asm16` and `asm_gpu16` are, so it has the same
command line (source on stdin, words on stdout, `--hex`, `--debug`,
`--sep_with_line`) and the same three backends.

Operands are **comma separated** and **typed**, as `gpu16`'s are, because
they are not all the same kind: `ld r3, r4, 2` names two registers and a
displacement and `movi r3, -1` names a register and an immediate. Registers
are `r0` to `r15`. Numbers are decimal or `0x` hexadecimal, and may be signed.
Comments run from `#` to the end of the line. A label is a token ending in
`:`.

| shape | instructions |
|---|---|
| `op rd, rs` | `and or not xor add adc sub sbb neg mul div mov cmp tst shl shr sar rol ror ldb stb sxb min max` |
| `op rd, sh` | `shli shri sari roli rori`, `sh` in 0..15 |
| `op rd, imm8` | `movi movih addi cmpi andi ori` |
| `op rd, rs, off4` | `ld st`, `off4` in 0..15 |
| `op rs` | `jmpr callr` |
| `op rd, sys` | `rd_sys`, `sys` in 0..2 |
| `op` | `halt nop ret` |
| `op label` | the fifteen branches, `jmp`, `call` |

Immediate ranges the assembler enforces: `movi`, `andi`, `ori` and `movih`
take -128..255 (both spellings of the same eight bits), `addi` and `cmpi`
take -128..127, because their immediate is sign extended and a value above
127 would silently mean a negative number.

`la rd, label` is the one pseudo instruction, and here it assembles to
**two** words - `movi rd, low_byte` then `movih rd, high_byte` - carrying the
label's **byte** address, which is twice its instruction word index. It is
what `jmpr`/`callr` want, and unlike `cpu16`'s three word expansion or
`cpu8`'s ten word one, it reaches the entire address space.

A label used as a branch, `jmp` or `call` operand is resolved to a
displacement in instruction words from the following instruction, and the
assembler rejects one that does not fit the 8 or 12 bits available.

## 10. Worked encodings

These are the check in this document that the assembler and the RTL read the
same bits, and they are reproduced in `tests/cpu_16_16_16_16_encoding.s` and
its expectation file.

| source | word | how |
|---|---|---|
| `and r1, r2` | `0x0021` | R, op 0x00, rs 2, rd 1 |
| `add r15, r0` | `0x040f` | R, op 0x04, rs 0, rd 15 |
| `sub r3, r4` | `0x0643` | R, op 0x06, rs 4, rd 3 |
| `mov r7, r8` | `0x0b87` | R, op 0x0b, rs 8, rd 7 |
| `cmp r1, r1` | `0x0c11` | R, op 0x0c |
| `shli r5, 3` | `0x1335` | R, op 0x13, the `rs` field is the shift |
| `sari r2, 15` | `0x15f2` | R, op 0x15, shift 15 |
| `ldb r6, r7` | `0x1876` | R, op 0x18 |
| `jmpr r9` | `0x1d90` | R, op 0x1d, rs 9, rd unused and zero |
| `rd_sys r4, 1` | `0x1f14` | R, op 0x1f, the `rs` field is the sysreg |
| `halt` | `0x2000` | R, op 0x20 |
| `ret` | `0x2200` | R, op 0x22 |
| `movi r3, 0x7f` | `0x47f3` | I, class 4, imm 0x7f, rd 3 |

## 11. What is deliberately not here

Stated so that nobody has to read the RTL to find out, and so that the list
can be argued with:

* **No three address form.** Section 1.
* **No `xori`, `subi`, `muli`, and no immediate for the byte accesses.**
  Section 3.2 - each costs a sixteenth of the encoding space.
* **No signed division, no remainder, no high half of a multiply.** `div` is
  unsigned and `mul` keeps the low 16 bits, as `cpu16.v`'s do. A 16x16 to 32
  multiply would need two destination registers and the two address form has
  one.
* **No stack pointer, no `push`/`pop`, no hardware stack.** Section 6.
* **No exceptions, interrupts, privilege, timer, MMU or atomics.** The same
  "not one of them, not even a stub" that `docs/cpu32_linux.md` section 1.1
  records for `cpu16.v`. Class 0xf and 29 R opcodes are held free for them.
* **No self modifying instruction memory.** `cpu16.v`'s `ld_p`/`st_p` have no
  successor here; the instruction space is reachable only by the loader.
* **No unaligned halfword access.** Section 5.
* **No delay slot, and no visible pipeline.** Section 8.
